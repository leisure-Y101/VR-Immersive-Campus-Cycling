# 沉浸式虚拟骑行系统 · 数据链路方案分析报告

| 项目 | 内容 |
| --- | --- |
| 报告名称 | 自行车传感器数据接入头显（Pico 独立版）方案分析 |
| 版本 | v1.1 |
| 日期 | 2026 年 10 月 |

---

## 一、背景与需求

**目标**
将自行车获取的运动数据，低延迟地送入 Pico 头显独立运行的 Unity 应用中，驱动虚拟场景随骑行运动。

**关键约束**
1. **Pico 头显不带 ANT+ 接收**（只有蓝牙/WiFi/USB）；
2. **延迟目标 < 20ms**；
3. 骑行场景**不宜拖线**；
4. 目标是**产品化**（用户不应额外购置电脑）；
5. 单人开发，需**分期落地**；
6. 数据类型：**标准量**（速度、踏频、心率）+ **自定义量**（IMU 姿态、转向角）。

**术语**
- **采集端/节点**：车侧负责收集传感器数据并向外发送的硬件（MCU / 树莓派 / PC）。
- **主机**：运行 Unity 应用并显示的设备（Pico 头显）。

## 二、原子方法（可组合的最小单元）

### 传输通道

| 方法 | 原理 | 延迟 | 带宽 | 说明 |
| --- | --- | --- | --- | --- |
| **A. BLE** | 蓝牙低功耗，GATT 通知 | 15–40ms（可调至 7.5ms 间隔） | 低（实用几十 kbps） | 头显自带蓝牙，可直连 |
| **B. Wi-Fi (UDP)** | 局域网 UDP 数据报 | **2–10ms** | 高（Mbps+） | 延迟最低、带宽大 |
| **C. USB-C 有线** | OTG 直连 | 1–5ms | 高 | 延迟最低，但**拖线** |
| **D. ANT+** | 2.4G 专有协议，经 USB 接收器 | 依广播周期（10–100ms） | 低 | 骑行传统协议，头显无内置 |

### 采集端形态

| 形态 | 说明 | 成本 | 功耗 |
| --- | --- | --- | --- |
| **无节点** | 传感器自身广播（BLE/ANT+） | 0 | 低 |
| **MCU 节点** | ESP32/nRF 聚合数据后转发 | 低（~10–50元） | 低 |
| **树莓派中枢** | 收 ANT+/BLE + 处理 + 转发 | 中（~300–600元） | 较高 |
| **PC** | 收 ANT+ + 跑重算法 + 转发/串流 | 高 | 高 |

## 三、架构组合（原子方法 → 完整方案）

### 方案一：传感器 ↔ 头显 直连 BLE
```
[BLE传感器: 速度/踏频/心率] ──BLE──> [Pico头显 Unity]
```
- 组合：方法 A + 无节点
- **现代 VR 健身主流**

### 方案二：车侧 MCU 节点 → BLE/WiFi → 头显
```
[各类传感器] → [ESP32/nRF 采集节点] ──BLE 或 WiFi──> [Pico头显 Unity]
```
- 组合：MCU 节点 + A 或 B
- 适合含**自定义量（IMU/转向角）**的场景

### 方案三：树莓派中枢 → WiFi UDP → 头显
```
[ANT+/BLE传感器] → [树莓派: openant/蓝牙] ──WiFi UDP──> [Pico头显 Unity]
```
- 组合：树莓派中枢 + B
- 保留现有 ANT+ 设备时的现实方案

### 方案四：PC 中转（开发期）
```
[ANT+棒] → [PC: 接收+算法] ──WiFi/UDP 或串流──> [Pico头显]
```
- 组合：PC + B
- 开发/验证期使用，**产品期应替换**

### 方案五：ANT+ 棒插头显有线
```
[ANT+棒] ──USB-C OTG──> [Pico头显]
```
- 组合：方法 C + D
- 延迟低但**拖线**，骑行不现实

## 四、方案对比矩阵

| 方案 | 延迟 | 带宽 | 额外硬件 | 复杂度 | 产品化 | 扩展性(自定义数据) |
| --- | --- | --- | --- | --- | --- | --- |
| 一 · BLE 直连 | 中 | 低 | 无 | 中(多连接管理) | ★★★★★ | ★★ |
| 二 · MCU 节点 | 低-中 | 中-高 | 1 块小板 | 中 | ★★★★ | ★★★★★ |
| 三 · 树莓派中枢 | 低 | 高 | 树莓派 | 中-高 | ★★★ | ★★★★ |
| 四 · PC 中转 | 低 | 高 | PC | 低(开发友好) | ★ | ★★★★ |
| 五 · 有线 | 最低 | 高 | ANT+棒 | 低 | ★ | ★★ |

## 五、各方案利弊详述

### 方案一：BLE 直连
- **利**：无额外硬件、体验最简、贴合主流；产品化最佳。
- **弊**：头显需同时连多个 BLE 设备，**连接管理复杂**；带宽低，**难承载高频 IMU**；部分传感器仅 ANT+ 不支持 BLE。

### 方案二：车侧 MCU 节点
- **利**：**统一时间戳**、可聚合自定义数据、头显只连一个设备；可走 BLE 或 WiFi；成本低、可埋入车内。
- **弊**：多一块硬件与电池；需自研固件与协议。

### 方案三：树莓派中枢
- **利**：可使用**现有 ANT+ 棒**（openant 库）；算力较强，可跑轻量处理；WiFi UDP 延迟低。
- **弊**：体积/功耗/成本较高；产品阶段通常需替换为更小方案。

### 方案四：PC 中转
- **利**：开发调试最方便；算力充足（视觉算法）；生态成熟。
- **弊**：**产品化不可接受**（用户要买电脑）；体量大、功耗高。

### 方案五：ANT+ 有线直连
- **利**：延迟最低，无需无线。
- **弊**：**拖线**，骑行场景基本不可行。

## 六、关键结论与推荐

### 开发期 → 产品期
| 阶段 | 推荐方案 | 理由 |
| --- | --- | --- |
| **开发期** | 方案四（PC 中转） | 调试方便、算力足，快速跑通链路 |
| **产品期** | 方案一 + 方案二组合 | 标准量 BLE 直连；自定义量走 MCU 节点；无 PC |

### 推荐最终形态
```
标准量(心率/速度/踏频) → 现成 BLE 传感器 ─┐
自定义量(IMU/转向角)   → ESP32采集节点(BLE)─┴─→ Pico头显(Unity)
```

### 选型原则
1. **标准量走现成 BLE 传感器**（贴主流、即插即用）；
2. **自定义量走车侧 MCU 节点**（ESP32 聚合成一路 BLE）；
3. **开发期允许 PC 中转**，但代码需将"数据接收层"抽象为独立模块，便于日后替换；
4. **尽量集中（都在头显端）**以满足 <20ms。

### 待决策项
- 传感器最终采用 **BLE** 还是保留 **ANT+**；
- 是否引入车侧 MCU 节点（涉及自研固件）；
- 视觉算法（姿态/摔倒）运行位置（头显端 / 边缘盒子）。

## 八、重点对比：BLE 直连 vs 中枢中转

### A. 传感器 BLE 直连头显
```
[BLE传感器: 心率/速度/踏频] ──BLE──> [Pico头显 Unity]
```

### B. 车上中枢 + WiFi UDP
```
[传感器] → [树莓派/ESP32 中枢] ──WiFi UDP──> [Pico头显 Unity]
```

| 维度 | A. BLE 直连 | B. 中枢 + WiFi |
| --- | --- | --- |
| 延迟 | 约 15–40ms（间隔可调 7.5ms） | **约 2–10ms（更低）** |
| 带宽 | 低（几十 kbps） | **高（Mbps 级）** |
| 额外硬件 | **无**（头显自带蓝牙） | 中枢（树莓派/ESP32） |
| 体积/功耗 | 低 | 较高 |
| 复杂度 | 头显多连接管理麻烦；Unity 端写 BLE | 中枢接收+转发 |
| 产品化 | ★★★★★ | ★★★ |
| 扩展性(自定义数据) | ★★ | ★★★★★ |
| 可靠性 | 2.4G 拥挤、多连接易掉 | 局域网易控 |

**结论**
- 想要**带宽高、延迟低** → 选 **B（WiFi UDP）**；
- 想要**零额外硬件、最简** → 选 **A（BLE 直连）**；
- **最佳组合**：标准量走 BLE 直连，自定义量走一个节点。

## 九、采集端为 ANT+ 时的可行性

**核心结论：ANT+ 传感器无法使用"BLE 直连头显"方案。**

原因：**Pico 头显只有蓝牙(BLE)，没有 ANT+ 无线电**；ANT+ 必须经**专用接收器**（本研究已有的两根 ANT+ USB 棒）。

> 注意区分：
> - **ANT+ 直连头显** → ❌ 不可行（头显无 ANT+ 无线电）；
> - **ANT+ → 树莓派 → 头显** → ✅ **可行，且为当前最现实路径**。

**推荐可行链路**
```
ANT+ 传感器 ──ANT+──> [树莓派4/5 + ANT+USB棒] ──WiFi UDP/BLE──> [Pico头显 Unity]
                         (openant 收数据)              (转发)
```

| 路径 | 说明 | 推荐度 |
| --- | --- | --- |
| ① 树莓派 + ANT+ 棒 → WiFi/BLE → 头显 | 即方案三 | ★★★★★ |
| ② 车上带 ANT 的 MCU（如 nRF52）→ 转 BLE/WiFi | 体积小、可隐藏 | ★★★★ |
| ③ ANT+ 棒插头显 USB-C(OTG) | 理论可行，Android 端驱动复杂 | ★★ |

**重要提示**
- 多数成品传感器为**双模（ANT+ 与 BLE）**，若支持 BLE，切换为 BLE 模式即可使用方案 A；
- 若**仅有 ANT+**，则"只有自行车 + 头显"不成立，**必须引入接收节点**。
