## 1. 用户确认的目标

将骑行软件与全景视频一起打包为一个 Android APK，安装在 PICO 4 Pro 上运行：

- 视频在头显本地读取、解码和显示，不使用 PICO Connect 进行画面串流。
- 头部追踪、菜单、骑行控制、HUD、训练统计均由头显本地完成。
- PC 在骑行时只负责通过 BLE 接收 A1 数据，并通过局域网转发给头显。
- PC 在制作阶段仍用于 Pro 2 视频拼接、稳定、编码和 Unity 开发。
- 优先改善画质、稳定性和舒适性，以真机验证选择最终播放规格。
- 保留当前能运行的 PC 版本和已有功能，使用独立测试场景验证后再迁移正式场景。

**当前实施与验收素材为5.7K/30fps和4K/60fps。** 用户已确认目前没有8K/60样片；其中“5.7k3.fps”按5.7K/30fps理解，执行时读取文件确认真实帧率。先完成现有两种素材的本地播放改造、变速及长时间测试，不等待Pro 2或8K素材。

## 5. 目标模块划分

```text
Pro 2原片 → PC离线拼接/稳定/编码 → 高质量母版与播放版本
                                          ↓
                                APK内置视频资源
```

建议脚本放在`Assets/Scripts/Video/`、`Assets/Scripts/Telemetry/`等合适目录；已有等价模块则复用。建议职责如下，名称可按工程风格调整，避免过度抽象：

| 模块 | 职责 |
|---|---|
| 视频后端接口/适配器 | 加载、准备、播放、暂停、变速、进度、结束/错误事件、诊断信息 |
| 包内视频解析与释放 | 解析资源位置；必要时流式释放；版本校验和错误恢复 |
| 全景显示 | 视频纹理及布局、正确材质、方向、全景投影 |
| A1遥测接收 | 接收、解析、丢弃旧包、本地超时判断、状态事件 |
| 骑行播放控制 | 实测功率→虚拟速度→受限平滑播放速度，起停状态管理 |
| 播放诊断 | 实际尺寸、帧率/帧时间、错误、丢帧和测试记录 |

接口需要兼容当前应用真正用到的时间、时长、暂停、恢复和循环语义。先搜索所有`VideoPlayer`引用，再确定适配范围；不要只替换一个脚本导致菜单、统计失效。

## 7. 阶段B：样片与系统播放器基准

### 样片要求

从现有5.7K/30和4K/60文件中各选30～60秒，尽量包含路牌、树叶、建筑、地面与运动目标。保留母版，不反复有损转码。若两段并非同一路线、同光照或同拍摄速度，不能将观感差异全部归因于分辨率或帧率；核心比较是同一文件在系统播放器、旧Unity路径、新OES/Skybox路径中的表现。

| 规格 | 用途 |
|---|---|
| 3840×1920、真实60/59.94fps | 当前必测：运动连续性、基础链路与骑行变速 |
| 5760×2880、真实30/29.97fps | 当前必测：高分辨率细节、解码兼容与骑行变速 |
| 6K60、8K30、8K60 | 当前无素材，不作为验收门槛；取得真实素材后另行测试 |

先读取文件真实参数，不凭文件名判断。当前可核对历史5.7K文件`D:\freebikeapk\nighttest360vidio_original_hevc.mp4`与4K60文件`D:\freebikeapk\360vidio\daytimetest.mp4`，但不要假设它们就是用户最后重新导出的版本。不得将X3的5.7K/30放大或插帧后标记为原生8K/60。

### 制作建议

- 当前X3原片使用对应Insta360 Studio工作流，5.7K/30保留5760×2880和原帧率，4K/60保留3840×1920和原帧率。后续Pro 2素材使用对应Insta360 Stitcher工作流，保留全部镜头及配套数据。
- 优先单目360等距柱状、2:1比例；双目不进入首阶段。
- 播放版优先HEVC、8-bit、4:2:0、SDR/BT.709，记录完整编码参数。
- 当前优先使用原分辨率高质量导出文件；若解码不兼容，先检查编码、profile/level和播放后端，保留原分辨率制作兼容版本。不要无条件套用统一码率。后续8K样片可从约60/80Mbps做对比，码率是测试起点，不是保证值。
- 原帧率原样保留，不强行把29.97写为30或59.94写为60。
- 检查曝光、拼接、前进方向、地平线、运动模糊和保护镜设置。

### 系统播放器对照

同一文件先在PICO本地360播放器中使用单目360模式观看。记录可播放性、清晰度、运动连续性和异常；再比较APK。系统播放器正常不能替代APK性能验证。

## 8. 阶段C：播放器选择与OES后端

### 先决条件

优先验证支持Android高分辨率硬件HEVC解码、OpenGLES3 OES纹理、暂停/恢复/变速的成熟播放器。可选AVPro Video当前兼容版本，但需要核对实际授权与Unity/PICO兼容性。

AVPro v3文档说明OES不在试用版提供。没有授权时：

- 不把非OES试用结果当作OES性能结果。
- 先建立适配接口、测试UI、资源加载及当前内置播放器对照。
- 明确列出需要用户提供的插件版本/许可，避免伪造插件API或空实现。

### 操作

1. 查看实际安装版本的文档和API，先打包运行供应商最小示例。
2. OpenGLES3为初始测试路径；AVPro可优先测试Media3/ExoPlayer。
3. 使用`YCbCr420_OES`与该版本提供的Android OES专用全景Skybox着色器。
4. 单目视频关闭错误的上下/左右分割，核对旋转、翻转、色彩与接缝。
5. 不把OES纹理绑定到不支持它的普通URP材质。
6. 避免额外Resolve/Blit/RenderTexture及CPU读回；如必须使用，记录原因与尺寸。
7. 若该版本文档要求URP关闭SRP Batcher，仅调整测试RP Asset并做记录；不要照旧帖无差别关闭所有批处理。
8. 检查解码器名称、是否硬件解码、源尺寸和输出尺寸。播放器未提供指标时用Android日志或原生诊断补充，不显示虚构数据。
9. 用当前普通球体路径与新OES/Skybox路径做同文件对照。

### 验收

- 视频方向/布局/颜色正确，无黑屏、异常缩放和花屏。
- 源文件及解码输出尺寸已确认。
- 硬件解码路径有证据。
- 1.0倍播放及暂停/恢复正常。
- 无每帧大块托管分配、视频CPU读回或重复播放器实例。

## 9. 阶段D：视频随APK交付

### 资源位置

建议使用`Assets/StreamingAssets/Videos/`保存包内播放素材，并提供轻量清单记录文件名、版本、规格、字节数及哈希。先检查视频导入/打包配置，避免Unity额外转码、重复包含或意外降分辨率。

### 路径一：直接读取

播放后端明确支持Android APK内StreamingAssets时，按其路径协议读取；验证打包压缩方式、随机访问、暂停和变速。Android包内路径不能用普通`File.Exists`作为唯一有效性判断。

### 路径二：首次启动释放

后端不支持高效包内读取时：

1. 在加载界面显示释放进度，检查存储空间。
2. 从APK资源流式复制到`Application.persistentDataPath`下的版本目录。
3. 先写临时文件，完成后校验字节数/哈希再标记可用。
4. 中断、空间不足、校验失败有明确恢复入口，未完成文件不能交给播放器。
5. 重启后复用已校验文件；版本改变再释放。旧版本清理要限定到应用自己管理的文件。
6. 大文件不能整体加载到byte[]/MemoryStream再复制；需根据Unity与播放器支持实现流式读写。

该方式仍满足一个APK安装，但可能同时占用APK视频与释放副本的空间。记录首次准备时间及实际存储需求。

### 验收

- 卸载测试版、重新安装后，无需手工复制视频即可启动路线。
- 无视频网络请求；网络断开不影响本地视频加载和环顾。
- 首次释放、二次启动、复制中断恢复已验证。
- 最终APK及实际安装体积有记录；若分发渠道有限制，明确指出，不静默改成外部下载。

## 10. 阶段E：渲染配置与诊断

### 初始配置

- Render Scale=1.0；测试时关闭动态分辨率。
- 关闭景深、运动模糊、色差、颗粒、无必要阴影/深度/不透明纹理。
- 无光照全景背景；MSAA先沿用已验证兼容的Android配置，不照搬PC参数。
- 注视点渲染测试时关闭或固定档位并记录，避免自动变化干扰对照。
- 优先验证90Hz；设备支持的其他刷新率作为对照，不调用未支持的值。
- 不能把Render Scale=1.0或面板2160×2160当成实际眼纹理尺寸。

### 诊断显示及日志

至少记录：

- APK/素材/播放器/Unity/SDK/OS版本。
- 文件分辨率、编码、位深、帧率与码率。
- 实际解码尺寸和输出纹理尺寸。
- XR实际每眼渲染尺寸、实际刷新率。
- 播放状态、播放速度和当前时间。
- 应用帧时间；可获得时记录CPU/GPU帧时间。
- 解码丢帧、错误；指标不可获得时明确写“不可获取”，不能用应用FPS替代。
- 测试持续时间、可获得的温度/热状态、内存及A1状态。

诊断UI低频刷新，日志以状态变化/汇总为主，不每帧刷屏。性能测量使用PICO Metrics HUD等设备工具补充。

60fps视频与90Hz显示并不整除；30fps/90Hz虽然重复节奏整齐但运动采样少。分别评估视频运动与头动响应，不宣称任一组合必然最舒服。

## 11. 阶段F：A1桥接与骑行播放控制

### 通信

1. 保留现有A1非标准协议解析，先确认实际测量是功率；速度/踏频为估算值时明确标记。
2. PC配置头显目标IP，使用UDP单播，端口与现有占用核对；当前方案使用50506。
3. 设计可版本化数据包：协议版本、会话ID、序号、测量更新时间/新鲜度、功率、连接及有效性状态。
4. 兼容或明确迁移现有纯数字包格式，PC和头显同步更新。
5. 头显用本地单调时间判断最后有效测量/接收超时。PC重复发送旧功率时不能伪装成新测量。
6. 丢弃旧包；PC重启/新会话允许序号复位，超时和恢复有状态事件。
7. 可约10～20Hz转发最新状态；不把发送频率当成A1真实采样率。
8. 核查INTERNET等必要权限和局域网/防火墙；只增加实际必要配置。

### 播放控制

1. 数据有效性检查 → 功率平滑 → 简单虚拟骑行模型 → 目标速度 → 播放时钟。
2. 素材有拍摄参考速度时使用该速度映射；没有时使用注明为估算的标定值。
3. 固定1.0倍基准通过后，先验证约0.9～1.1倍，再扩大范围。
4. 限制播放速度变化率；接近停止时使用明确状态机处理，不能把0.9倍突然切到0倍当作自然减速。
5. 起步/暂停阈值加入滞回和短暂稳定判定，避免阈值附近抖动。
6. 停踩与数据丢失分开处理；超时后平缓减速或暂停并提示，不无限使用旧功率。
7. 不每帧设置视频time/Seek来模拟骑行位置；对所有变速能力做播放器真机验证。
8. 保留暂停时头部自由环顾；视频解码故障时训练计时/距离不能继续无条件增长。

### 验收

- 起步、稳定踩踏、功率突变、停踩和恢复均无频繁暂停抖动。
- PC重启、BLE断线、Wi-Fi中断、旧包/乱序包的行为明确。
- 后端更换后菜单、统计、暂停和结算语义一致。

## 14. 性能不足时的排查顺序

| 现象 | 优先检查 |
|---|---|
| 系统播放器清楚、APK模糊 | 实际眼纹理尺寸、纹理采样、Skybox、额外缩放/中间输出 |
| APK视频卡，应用帧时间正常 | 硬件解码、编码级别、视频帧调度 |
| 转头也卡，GPU帧时间高 | 纹理转换/复制、渲染负载、后处理、过量超采样 |
| 热机后变差 | 热状态、降频、资源泄漏/积累 |
| 固定速度正常、变速异常 | 后端变速支持、速度控制频率、时钟与音频 |
| 包内失败、释放后正常 | APK资源读取协议、压缩与随机访问 |
| OES变换异常 | 对应版本URP兼容说明、材质与批处理配置 |
| 切视频崩溃 | 解码实例生命周期、同时驻留视频、版本问题、峰值内存 |

确认原因后再调整编码/分辨率/帧率。完整8K无法稳定时，选择实测稳定版本交付并保留母版。

分块/视野相关解码属于后续独立研发：需要离线编码布局、基础全景兜底、视野预取、同步及变速支持。不能简单拆文件后同时播放，也不能假设CrystalView可直接嵌入本应用。
