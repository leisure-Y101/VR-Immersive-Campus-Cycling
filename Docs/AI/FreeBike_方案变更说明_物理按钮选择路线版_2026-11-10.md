# FreeBike 方案变更说明

## 物理按钮选择路线版（2026-11-10）

> **本文件是原同事 A、同事 B 交接文档的增补与变更说明。**
> 请将本文件与原交接文档一起阅读。若原文档与本文件在第一阶段范围、场景切换方式、路线选择方式或岗位职责上存在冲突，以本文件为准。

## 0. 本次变更的核心结论

项目第一阶段不再开发 3D 岔路口，也不使用真实车把转向角来实时控制虚拟骑行轨迹。体验者到达预设路口后，通过安装在自行车把手附近的**物理按钮模块**，手动选择左转、直行或右转；Unity 根据选择播放预先拍摄好的对应 360° 转向视频。

第一阶段采用：

**360° 2D 全景视频道路 + 视频时间轴路口触发 + 物理按钮手动选择 + 预录转向视频 + 分段加载。**

目标运行平台仍然包括两种：

1. **PC VR 模式**：Windows PC 运行 Unity，通过 PICO Connect 串流到 PICO 4 Pro。
2. **PICO 独立模式**：Unity Android 程序直接安装在 PICO 4 Pro 内运行，视频从头显本地存储读取。

两种运行模式共用路线逻辑和路线清单；视频文件可以根据平台选择不同的分辨率、码率或编码版本。

## 1. 已确认的方案与仍需验证的事项

为避免把建议误认为已经完成的决定，本文件将内容分为三类。

### 1.1 已确认的第一阶段方案

| 项目 | 第一阶段决定 |
|---|---|
| 校园道路画面 | 使用 Insta360 Pro 2 拍摄的 360° 2D 单目全景视频 |
| 采集目标规格 | 优先采集 8K 2D 60fps；后期拼接输出目标为 7680×3840、2:1 等距柱状视频 |
| 立体视频 | 第一阶段不制作、不依赖 3D 立体 360° 视频 |
| 岔路口 | 暂时不搭建 3D 路口场景 |
| 路线选择 | 使用物理按钮手动选择左转、直行、右转 |
| 转向表现 | 选择后直接播放对应方向预先拍摄的 360° 转向视频 |
| 真实车把角度 | 第一阶段不作为路线分支判定依据；Kinect、AS5600/AS5048A 转向角方案暂缓接入 |
| 路线播放 | 根据当前视频路段、路口触发时间和按钮选择，决定下一段视频 |
| 资源管理 | 视频分段存储、按需播放；不把全部视频同时交给解码器 |
| 播放平台 | PC VR 串流与 PICO 4 Pro 独立运行都要支持 |
| A1 功率 | 继续作为虚拟骑行视频播放速度/前进速度的数据来源 |

### 1.2 已提出、建议采用，但需要原型验证的实现细节

| 项目 | 建议做法 | 验证内容 |
|---|---|---|
| 路口等待画面 | 优先显示路口 360° 静态照片；也可使用当前视频冻结帧作为临时等待画面 | 静态图方向、位置是否与进路口视频匹配；是否造成视点跳变 |
| 物理按钮数量 | 第一版建议左转、直行、右转、确认四个按钮 | 按钮大小、布局、盲操作可达性、误触率 |
| 按钮通信 | PC 原型先用 USB 键盘/标准游戏手柄输入；双平台候选方案为 ESP32-C3 BLE HID Gamepad | PICO 4 Pro 对 BLE HID 控制器的配对、按键映射和长时间稳定性必须实测 |
| 视频播放器数量 | 第一版优先一个主 VideoPlayer；同一时刻只播放/解码当前视频 | 切换准备时长、黑屏时间、内存峰值；必要时再评估双播放器 |
| 视频编码 | 以 HEVC/H.265、8-bit、4:2:0、SDR BT.709 作为首轮测试配置 | PC 与 PICO 独立版硬解兼容性、码率、帧率和温度 |
| 运行画质 | 8K 版本先测试；准备 6K/4K 降级版本 | 不能仅凭 PC 5090 测试结果判断 PICO 独立版可稳定运行 8K |

### 1.3 第一阶段明确不作为交付目标的内容

- Unity 小范围 3D 岔路口场景、3D 路面和出口碰撞体。
- 通过车把转角连续控制 3D 虚拟自行车轨迹。
- Kinect 骨骼转向接入当前主线。
- AS5600/AS5048A 转向角传感器固件及数据接入。
- 根据虚拟轨迹或碰撞体自动判定左/直/右出口。
- 多个 8K 视频同时解码、多个 VideoPlayer 常驻播放。
- 真实骑行台的物理制动或阻力控制。

这些内容不代表永久取消，而是从第一阶段范围中移出，避免影响手动路线选择版本先完成端到端 Demo。

## 3. 新的用户体验与路线播放流程

### 3.1 第一阶段完整流程

```text
主页 / 开始骑行
      │
      ▼
播放 Road_001.mp4
A1 功率控制视频播放速度
      │
      ▼
到达预设路口触发点（视频时间轴）
      │
      ▼
暂停当前视频，锁定自动恢复播放
      │
      ▼
显示路口 360° 静态照片或冻结画面
      │
      ▼
物理按钮选择：左转 / 直行 / 右转
      │
      ▼
按确认键提交 BranchChoice
      │
      ▼
路线管理器根据 Manifest 查找对应视频
      │
      ▼
停止/释放旧视频，Prepare 已选视频
      │
      ▼
等待 prepareCompleted，并检查首帧可用
      │
      ▼
从静态等待画面淡出，开始播放所选转向视频
      │
      ▼
回到普通骑行状态，A1 继续控制播放速度
      │
      ▼
转向片段播放结束，进入下一段道路或下一个路口
```

### 3.2 路口选择状态机

第一阶段建议使用以下状态：

```csharp
public enum RoutePlaybackState
{
    Riding,             // 正常播放道路视频
    JunctionPrompt,     // 到达路口，等待选择
    ChoiceSelected,     // 已选择方向，尚未确认
    PreparingNext,      // 准备用户确认的下一段视频
    Transitioning,      // 静态画面与新视频之间转场
    Failed              // 资源不存在或 Prepare 失败
}
```

规则：

1. 只有 `Riding` 状态接受路口触发事件。
2. 进入 `JunctionPrompt` 后，必须锁定自动播放恢复；即使体验者仍在踩踏，A1 的功率也不能绕过路线选择流程调用 `Play()`。
3. 方向按钮只改变当前高亮选择，不立即切换视频。
4. 确认按钮提交选择；提交后本次路口选择锁定，忽略重复按键，直到进入下一路口。
5. 只有用户确认的方向才能进入 `PreparingNext`。
6. 视频文件不存在、解码失败或 Prepare 超时，保持在等待画面并提供重试/回退；不能黑屏后假定切换成功。
7. 新视频准备成功后，才进入 `Transitioning` 并开始播放。
8. 退出或取消路线选择的行为由负责人确认；第一版不得在未选择时随机选择出口。

### 3.3 路口触发必须使用视频时间轴

当前 A1 功率会改变 `VideoPlayer.playbackSpeed`，因此真实经过的秒数与视频播放时间并不相同。

路口触发必须使用 `VideoPlayer.time` 或统一的路线媒体时间，而不能简单用 `Time.time` 或“开始骑行后经过 30 秒”作为触发条件。

路线清单需要记录：

- 当前视频 ID；
- 路口触发时间 `promptAtSeconds`；
- 路口 ID；
- 等待用 360° 静态图片（可选）；
- 可选方向及对应视频 ID；
- 下一段视频起始方向/拍摄信息；
- 每个视频的素材版本与运行平台资源路径。

## 4. 物理按钮模块：第一阶段接口约定

### 4.1 第一版按钮定义

建议使用四个按钮：

| 按钮 | 事件 | 功能 |
|---|---|---|
| 左转 | `SelectLeft` | 高亮左转选项 |
| 直行 | `SelectStraight` | 高亮直行选项 |
| 右转 | `SelectRight` | 高亮右转选项 |
| 确认 | `ConfirmSelection` | 提交当前选择 |

第一版可以将方向选择与确认分开，减少骑行时误触。按键模块的最终外壳、按键排列和固定方式需要经过骑行者实际试用后确定。

### 4.2 输入实现路线

按以下顺序降低集成风险：

1. **PC 原型：** 用键盘或标准 USB 游戏手柄模拟四个按钮，先把 Unity 选择状态机跑通。
2. **物理按钮验证：** 使用 ESP32-C3 开发板和四个实体按钮，先在 PC 上通过 BLE HID Gamepad 或 USB 输入验证。
3. **PICO 兼容验证：** 通过 PICO 4 Pro 实机配对，检查设备是否被识别、按键映射、延迟、断连恢复和长时间稳定性。
4. **最终选型：** 若 BLE HID 在 PICO 上稳定可用，PC 与 PICO 共用该控制器；若不稳定，再评估 USB HID、PICO 手柄备用输入或 Android 原生 BLE GATT 插件。

**重要：** ESP32-C3 BLE HID 是候选方案，不是已经验证的 PICO 兼容结论。未经实机测试，不要把它写成“已完成”。

### 4.3 按键输入的数据接口

B 对外只需提供平台无关的路线选择事件，不把 ESP32、BLE、USB 或键盘细节暴露给 A：

```csharp
public enum BranchChoice
{
    None,
    Left,
    Straight,
    Right
}

public event Action<string, BranchChoice> BranchChoiceConfirmed;
```

事件参数建议为：

- `junctionId`：当前路口 ID；
- `choice`：用户确认的方向。

A 监听该事件后，根据路线配置查找目标视频。事件必须只提交一次，且带有当前 `junctionId`，避免重复按键或旧路口输入污染下一路口。

### 4.4 按键处理要求

B 必须处理：

- 按键防抖；
- 长按是否重复触发；
- 确认键在无方向选择时不提交；
- 路口选择状态之外忽略路线按键；
- 重复按键和蓝牙断连；
- 输入设备重新连接后的状态恢复；
- 按钮顺序和 UI 高亮一致；
- 选择后是否允许修改、何时锁定；
- 触发与确认事件日志。

## 5. 新的视频拍摄、命名和路线配置要求

### 5.1 Insta360 Pro 2 采集目标

第一阶段以 2D 单目 360° 全景为主，不拍 3D 立体全景作为运行素材。

| 项目 | 采集/制作目标 | 说明 |
|---|---|---|
| 相机 | Insta360 Pro 2 | 六镜头专业全景相机 |
| 模式 | 360° Pano / 2D Monoscopic | 不选择 Stereo 3D |
| 采集档位 | 优先 8K 60fps | 具体菜单命名以相机固件/官方软件版本为准 |
| 原始素材 | 完整保留六路镜头文件及配套项目/陀螺仪文件 | 不要只保存预览文件或最终 MP4 |
| 后期拼接目标 | 7680×3840、60fps、2:1 等距柱状 | 导出成功后用 ffprobe/MediaInfo 检查 |
| 首轮运行编码 | HEVC/H.265、8-bit、4:2:0、SDR BT.709 作为测试起点 | PC 与 Android 实机验证后再锁定 |
| 兼容素材 | 另备 6K、必要时 4K 版本 | 用于设备性能不足时降级 |

### 5.2 三脚架与移动支架的用途必须区分

- **固定三脚架：** 适合采集路口 360° 静态照片、固定点环境素材，或固定位置观察画面。
- **移动式刚性支架：** 适合沿道路移动拍摄连续第一人称骑行视频；相机必须牢固固定、水平、具备安全绳，并符合现场拍摄安全要求。

固定三脚架上的相机即使录制了 360° 视频，画面视点仍固定在同一个位置，不能代替沿道路移动拍摄的骑行视频。仅在原地旋转相机也不能得到真实的道路前进视差。

Pro 2 机身较重，移动拍摄前必须确认支架承重、锁紧结构和二次防脱装置；不能把相机直接安装在头盔上作为默认方案。

### 5.3 一个路口至少需要哪些素材

示例：`Junction_001`

```text
Junction_001/
├── Approach_001.mp4        # 从上一段道路接近路口
├── Junction_001_360.jpg    # 路口等待画面，可选但建议采集
├── Turn_Left_001.mp4       # 左转后的移动全景视频
├── Turn_Straight_001.mp4   # 直行视频
└── Turn_Right_001.mp4      # 右转视频
```

拍摄要求：

1. 左、直、右三段视频应从尽量一致的路口参考位置和初始朝向开始。
2. 相机高度、水平、曝光、白平衡和输出投影格式尽量一致。
3. 每段转向视频要包含真实的移动过程；不能只在三脚架上原地转动相机模拟转弯。
4. 建议开头保留短暂、稳定的画面，供后期校准入口方向；正式播放时可在编辑阶段决定是否裁掉。
5. 记录每条路线的起点、终点、方向、拍摄日期、相机高度和素材版本。
6. 在实际路口记录路口触发位置与各方向的对应关系。

### 5.4 视频分段原则

- 以道路自然节点、路口和路线分支为主要切分点，不要无意义地每几秒切一次。
- 长直道路可以按素材管理和切换需要进一步分段；分段长度需通过 Prepare 耗时、播放稳定性和文件管理体验确定。
- 普通道路视频在分支前结束或在预设触发点进入选择状态。
- 用户确认方向后只加载对应的转向视频，不同时 Prepare 左、直、右三个 8K 文件。
- 视频切分应检查关键帧、时间戳、音轨、起始帧与结束帧；避免依赖粗略文件切割导致片头黑帧或无法独立解码。

### 6.2 A → B / B → A 接口

| 事件/字段 | 方向 | 含义 |
|---|---|---|
| `JunctionPromptReached(junctionId)` | A → B | 当前视频到达路线选择点，进入选择状态 |
| `BranchChoiceChanged(junctionId, choice)` | B → UI/A | 当前高亮方向变化，尚未确认 |
| `BranchChoiceConfirmed(junctionId, choice)` | B → A | 用户已经确认方向，只触发一次 |
| `SelectionLocked(junctionId)` | B → 播放协调器 | 当前路口选择已提交，忽略重复按键 |
| `NextSegmentPreparing(segmentId)` | A → B/协调器 | 正在准备目标视频 |
| `NextSegmentPrepared(segmentId)` | A → B/协调器 | 目标视频已经准备好，可转场 |
| `SegmentPlaybackStarted(segmentId)` | A → B/协调器 | 新视频已经开始播放 |
| `RoutePlaybackFailed(segmentId, reason)` | A → 负责人/UI | 资源不存在、Prepare 失败或超时 |

注意：A 是路线与视频资源的唯一负责人，B 是物理输入与选择交互的唯一负责人。B 不直接修改 `VideoPlayer.url` 或调用 `Play()`；A 不直接读取 ESP32/BLE/USB 按键原始输入。

### 6.3 A1 播放控制必须设唯一所有者

当前仓库 `Assets/Scripts/PanoBikeSpeed.cs` 同时包含 UDP 50506 接收、功率映射播放倍速以及 `VideoPlayer.Play()` / `Pause()` 控制逻辑。

新架构必须避免多个组件同时控制视频播放状态：

- `PanoBikeSpeed` 或重构后的功率模块：负责接收 A1 功率、判断数据是否新鲜、计算目标播放速度。
- `VideoRouteManager` / 播放协调器：负责真正执行 `Play()`、`Pause()`、`Stop()`、`Prepare()` 和切换。
- `BranchSelectionManager`：负责路口选择状态锁，不直接操作 VideoPlayer。

路口选择期间必须有最高优先级的播放锁。A1 仍然可以继续接收功率，但功率不能解除路口选择锁，也不能在用户未确认分支时自动恢复视频。

这是本次集成的 P0 风险点，必须先完成设计，再进入真实 A1 联调。

## 7. 分段加载与资源释放规则

### 7.1 第一阶段的默认资源策略

**一个主 VideoPlayer + 当前片段按需播放 + 路口选择等待画面 + 只 Prepare 已确认的下一段。**

- 全部视频文件可以存放在 PC SSD 或 PICO UFS 中；文件存在于存储设备不代表同时进入 GPU。
- 运行时只打开当前需要的文件。
- 不要在场景启动时为所有路线片段创建 VideoPlayer。
- 不要同时 Prepare 同一路口的左转、直行、右转三个高分辨率视频。
- 路口选择画面优先使用 360° 静态照片或当前帧，不额外启动一个 8K 视频解码器。
- 确认方向后，停止/释放当前片段，再 Prepare 用户选择的单个视频。
- 新视频准备成功后才切换显示；失败则保留等待画面并提示重试。
- 普通停车使用 Pause；片段切换和资源回收使用 Stop。不要把二者混为一谈。

### 7.2 为什么第一版不默认使用双 VideoPlayer

双播放器可以缩短某些切换等待，但会增加同时准备的视频资源、解码表面、内存和可能的硬件解码占用。PC 上能运行双播放器，不代表 PICO 独立版也能运行。

因此第一版先实现单播放器切换，测量：

- `Prepare()` 耗时；
- `prepareCompleted` 到首帧显示的耗时；
- 路口等待画面持续时间；
- PC CPU/GPU Video Decode/显存/系统内存；
- PICO CPU/GPU 帧时间、内存、视频掉帧和温度。

只有当单播放器方案的加载等待无法接受，而且 PICO 实测证明双播放器可承受，才考虑双播放器方案。

### 7.3 运行时画质策略

| 平台 | 首轮测试 | 降级方案 |
|---|---|---|
| PC VR + PICO Connect | 8K 2D 60fps HEVC | 6K 60fps HEVC |
| PICO 4 Pro 独立版 | 8K 2D 60fps HEVC 先做单片验证 | 6K 60fps；仍不稳定再测试 4K 版本 |

上述是测试顺序，不是对设备稳定播放的保证。最终配置须以 Unity 实机测试、PICO 视频解码能力、运行温度和 VR 帧时间为准。

首轮编码建议从 HEVC/H.265、8-bit、4:2:0、SDR BT.709 开始；码率、profile、level、关键帧间隔和音轨策略需要用真实素材测试后冻结。PC 与 Android 不保证对所有 HEVC 文件参数的支持完全一致，必须制作兼容测试样本。

## 14. 最终验收定义（一句话）

**体验者戴上 PICO 4 Pro，通过 A1 功率控制校园 360° 全景道路视频前进；到达路口时，系统暂停并显示选择界面，体验者通过自行车上的物理按钮选择左转、直行或右转，Unity 只加载并播放对应的预录 360° 转向视频，随后继续下一段道路；该流程在 PC 串流和 PICO 独立运行两种模式下都经过实机验证。**

这就是第一阶段的交付目标。
