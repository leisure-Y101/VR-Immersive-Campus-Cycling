028 [Heading 2] 1.1  情境（Situation）
029 [Normal] 项目目标是在 PICO 4 Pro 上做一套校园 360° 沉浸式骑行 Demo：用户佩戴头显，在 PC 端 Unity 渲染的全景校园中骑行；真实自行车（ThinkRider A1 功率台）提供功率，经 BLE 桥接进入 Unity，驱动视频播放速度；交互只保留“开始 / 暂停 / 继续 / 退出”。硬件为 PICO 4 Pro + Windows PC（RTX 4060 Laptop 8 GB）+ A1 骑行台，PC 端通过 PICO 互联 + SteamVR + OpenXR 串流到头显。
030 [Heading 2] 1.2  冲突（Complication）
031 [Normal] 原工程功能很多（HUD、心率、报告、五语言、设置、射线菜单等），但演示只需要“看风景”。同时出现三个硬冲突：6.4K H.264 视频在 PC 上卡顿；应用在头显里不是全景而是 SteamVR 影院/桌面；A1 数据链路尚未在真实踩踏中验证。三者分别属于编解码、VR 运行时、数据链路三个层面，互相掩盖。
032 [Heading 2] 1.3  问题（Question）
033 [Normal] 如何在保留 8K 主页与 6K/4K 视频的前提下，做到：①视频不卡、不降分辨率；②应用真正进入头显的沉浸全景，而不是 SteamVR 面板；③A1 有功率才播放、停踩即暂停；④工程可重复构建、可交付？
034 [Heading 2] 1.4  答案（Answer）与范围
035 [Normal] 答案是把应用减到三段式，把视频转成硬件可解码的格式，把 A1 数据经 Python BLE 桥接为 UDP，并把“构建目录完整性、SteamVR 启动顺序、单实例焦点”作为交付前置条件。本报告覆盖 2026-10-26 至 2026-10-29 的设计、实现、联调与排障；不包含正式校园素材替换、长期稳定性测试与量产化工作。

055 [Heading 3] 3.3.1  视频与解码
056 [Heading 3] A1  6.4K H.264 361 Mbps 播放卡顿
057 [Normal] 现象：编辑器 Play 与 PC 构建里视频都卡；构建日志出现 “Failed to create the D3D11 device … software video decoding”。
058 [Normal] 根因：H.264 硬件解码通常上限 4096×4096；6400×3200 超出上限，只能软件解码；361 Mbps 码率进一步放大 CPU 压力，实测软件解码约 25 fps。
059 [Normal] 处理：用 ffmpeg NVENC 转 6.4K HEVC（130 Mbps），保留 6400×3200/59.94；另生成 4K H.264（70 Mbps）做兼容备份。
060 [Normal] 验证：ffmpeg -benchmark + hevc_cuvid 实测 131 fps；用户反馈 4K 版本“不卡了”；文件规格用 ffmpeg -i 核对。
061 [Normal] 状态：已缓解；Unity 端 4K 播放仍有独立错误（见 A2）。
062 [Heading 3] A2  Unity 报“主视频播不了，切换到兼容视频”
063 [Normal] 现象：Player.log：`CampusRideApp: 主视频播不了，切换到兼容视频 ...6k60fps_4k.mp4`；前一行有 `Unexpected timestamp values detected … H.264 videos not encoded with the baseline profile`。
064 [Normal] 根因：高概率是 H.264 High profile + B 帧 + 非 baseline 时间戳导致 Unity/MediaFoundation 准备失败；也可能叠加 D3D11 解码设备创建失败（A3）与多实例资源竞争。
065 [Normal] 处理：计划 baseline/CFR 重编码：`-profile:v baseline -bf 0 -fps_mode cfr -r 60000/1001`；或改用 4K HEVC。替换同路径文件不需要重新编译。
066 [Normal] 验证：待重编码后用同一场景复测，检查日志是否仍出现“主视频播不了”。
067 [Normal] 状态：未闭环（P0）。
068 [Heading 3] A3  D3D12 下 D3D11 视频解码设备创建失败
069 [Normal] 现象：日志：`Failed to create the D3D11 device` / `Dedicated video D3D11 device creation failed (error: 0x887a0004)`；随后全部走软件解码。
070 [Normal] 根因：Unity 的视频硬解通道走 D3D11（DXVA）。当播放器主设备是 D3D12、进程又是 Low integrity 时，单独创建 D3D11 设备会失败，硬件解码不可用。
071 [Normal] 处理：建议把 Player Graphics API 切到 D3D11（此前被拒绝执行，未改动）；C 盘 Medium 构建后先观察是否仍报错；用任务管理器 GPU 的 Video Decode 引擎确认是否硬解。
072 [Normal] 验证：待 D3D11 或 Medium 构建下复测；目前 4K 播放错误尚未排除此因素。
073 [Normal] 状态：待定。
074 [Heading 3] A4  6K 保清晰度必须用 HEVC，不能用 H.264
075 [Normal] 现象：用户明确要求“必须 6K60，不降分辨率、不掉帧”；但 H.264 6.4K 无法硬解。
076 [Normal] 根因：H.264 硬解上限 4096；HEVC（H.265）NVDEC 可到 8K。Windows 已安装 Microsoft.HEVCVideoExtension 2.5.33。
077 [Normal] 处理：生成 6.4K HEVC 主用文件，保留 4K H.264 作为兼容备份；场景按需要切换路径。
078 [Normal] 验证：NVDEC 131 fps；HEVC 扩展注册表存在；Unity 内 HEVC 最终播放仍需实机确认。
079 [Normal] 状态：文件就绪，最终播放待验证。
080 [Heading 3] 3.3.2  VR 运行时与显示
081 [Heading 3] B1  OpenXR RUNTIME_UNAVAILABLE：应用跑在 SteamVR 之前
082 [Normal] 现象：日志 `xrCreateInstance: XR_ERROR_RUNTIME_UNAVAILABLE`；头显里是平面/影院画面。时间线：13:04:48 应用启动，13:04:50 OpenXR 失败，13:05:02 SteamVR 才开始记录。
083 [Normal] 根因：Unity OpenXR 只在启动时初始化一次；SteamVR/OpenXR Runtime 未就绪就永久失败，之后不会重试，应用退化成桌面平面窗口。
084 [Normal] 处理：规定启动顺序：PICO 互联连头显 → 启动 SteamVR 并确认头显进入 SteamVR 主页 → 再启动应用；提供等待 vrserver 的启动脚本。
085 [Normal] 验证：13:46 日志出现 `Runtime Name: SteamVR/OpenXR`、`XR_SESSION_STATE_FOCUSED`、2644² swapchain，证明顺序修复有效。
086 [Normal] 状态：已解决（流程问题）。
087 [Heading 3] B2  DSH 工作区 Low integrity 导致 exe 无法访问 SteamVR
088 [Normal] 现象：日志第一行 `Process is running in low integrity mode...`；`icacls` 显示 `D:\freebikeapk` 与 `demo\freebike.exe` 为 `Mandatory Label\Low Mandatory Level`；OpenXR 仍 RUNTIME_UNAVAILABLE。
089 [Normal] 根因：DSH 工作区目录带有 Low 完整性标签，构建产物继承 Low。Low 进程被 Windows 完整性隔离，无法访问 Medium/High 的 SteamVR 共享资源与 OpenXR Runtime。
090 [Normal] 处理：把构建改到 `C:\Users\admin\Desktop\bikedemo`（Medium）；验证 `icacls` 无 Low 标签；日志不再出现 low integrity。
091 [Normal] 验证：新构建日志无 low integrity，OpenXR 成功 FOCUSED；这是本次最关键的隐藏坑。
092 [Normal] 状态：已解决。
093 [Heading 3] B3  SteamVR 500% 超采样导致 6976×6976/眼
094 [Normal] 现象：早期日志 `Recommended: Width=6976, Height=6976`，画面极卡。
095 [Normal] 根因：`D:\Steam\config\steamvr.vrsettings` 中 `supersampleManualOverride: true`、`supersampleScale: 5`（500%），把每眼像素放大约 10 倍。
096 [Normal] 处理：把渲染分辨率降到 Auto 或 100–150%；最新日志已降到 2644×2644。
097 [Normal] 验证：最新日志 Recommended 2644²；仍需在头显内确认帧率。
098 [Normal] 状态：已改善（需最终确认）。
099 [Heading 3] B4  多实例/焦点被抢，头显仍显示 SteamVR 影院层
100 [Normal] 现象：同一份 Player.log 中出现 3 个进程 PID（22724 / 43692 / 20300），并有 `FOCUSED → VISIBLE → SYNCHRONIZED`；用户描述“像壳，中间一个观察框”，确认是 SteamVR 界面。
101 [Normal] 根因：多个 freebike.exe 同时运行会抢 SteamVR 前台焦点与 UDP 50506；应用窗口不在前台时 SteamVR 显示仪表盘/影院层，头显里就不是应用画面。
102 [Normal] 处理：任务管理器结束全部 freebike.exe；只启动一个；在 PC 上点一下应用窗口保证前台；头显里按左手柄菜单键关闭 SteamVR 面板；必要时用手柄选中运行中的 freebike 窗口。
103 [Normal] 验证：最新单实例日志已 FOCUSED，但用户仍看到 SteamVR 界面，说明焦点/面板仍未真正切到应用。
104 [Normal] 状态：未闭环（P0）。
105 [Heading 3] B5  OpenXR 手柄 Profile 缺失，B/Grip 可能不映射
106 [Normal] 现象：日志 `Features requested to be enabled: Khronos Simple Controller Profile`，其余 Interaction Profile 均为关闭。
107 [Normal] 根因：Unity OpenXR 需要启用与 PICO Connect/SteamVR 暴露的手柄匹配的 Interaction Profile，否则 `InputDevices` 拿不到完整按键（尤其 B/Grip）。
108 [Normal] 处理：在 Project Settings → XR Plug-in Management → OpenXR（Windows）中启用 Oculus Touch / HTC Vive / Valve Index / KHR Simple 等 Profile；临时可用键盘 Enter 开始、按住 Esc 暂停。
109 [Normal] 验证：待配置后实机验证 Trigger/B/Grip。
110 [Normal] 状态：待配置。
111 [Heading 3] 3.3.3  场景、数据与交互
112 [Heading 3] C1  重复 PanoSphere / 两个 PanoBikeSpeed 抢 UDP 50506
113 [Normal] 现象：场景里有 `PanoSphere` 与 `PanoSphere (1)`，各带 VideoPlayer + PanoBikeSpeed；日志 `PanoBikeSpeed: UDP 50506 打开失败`。
114 [Normal] 根因：重复对象导致两个 UDP 监听、两个球体在 800 m 处重叠，A1 数据可能进错对象。
115 [Normal] 处理：在 `CampusRideApp.Awake()` 里关闭 `PanoSphere (1)`，保证只保留主球与一个 PanoBikeSpeed。
116 [Normal] 验证：日志出现 `已关闭重复的 PanoSphere (1)`；UDP 50506 正常监听。
117 [Normal] 状态：已解决。
118 [Heading 3] C2  A1 骑行台 BLE 数据链路验证
119 [Normal] 现象：需要确认真实踩踏时能否收到功率。
120 [Normal] 根因：A1 使用 CPS（0x1818 / 0x2A63）；PC 端 Python bleak 连接后把功率以 ASCII float 发到 127.0.0.1:50506。
121 [Normal] 处理：运行 `a1_bridge.py`（依赖 `.pydeps-ble`）；Unity 端 PanoBikeSpeed 监听 50506；关闭键盘 fallback。
122 [Normal] 验证：实测：Connected F5:79:6C:84:32:07；订阅 0x2A63；26–35 W；停踩 0 W；UDP 端口被 freebike.exe 占用。
123 [Normal] 状态：已打通（仅功率；踏频未解析）。
124 [Heading 3] C3  播放与自行车联动：有功率才播、停踩暂停
125 [Normal] 现象：早期为了 6K 直接播放，视频一进场景就自动播放，和自行车无关。
126 [Normal] 根因：`controlPlaybackState` 被设为 false、`idlePlayback=1`、StartRide 直接 Play，导致不踩也播。
127 [Normal] 处理：改回：`controlPlaybackState=true`、`idlePlayback=1`、`StartRide` 先 Pause；PanoBikeSpeed 在 `external && smoothedPower >= 5W` 时 Play，否则 Pause；`allowKeyboardFallback=false`。
128 [Normal] 验证：编译 0 error；A1 实测有功率/停踩；Unity 内联动待实机确认。
129 [Normal] 状态：已实现，待实测。
130 [Heading 3] C4  8K 主页纹理会不会拖垮电脑
131 [Normal] 现象：用户担心 7680×3840 的 8K 照片会卡。
132 [Normal] 根因：8K 静态纹理压缩后约 30–40 MB（未压缩约 118–157 MB），只加载一次、一个球体一次采样；RTX 4060 8 GB 完全够用；真正的负载是 500% 超采样与视频解码。
133 [Normal] 处理：保留 8K；如要省显存可把 Max Size 降到 4096；不视为性能瓶颈。
134 [Normal] 验证：资源规格与导入设置核对；无持续卡顿证据。
135 [Normal] 状态：结论：不影响，无需降级。
136 [Heading 3] 3.3.4  工程与交付流程
137 [Heading 3] D1  构建与场景/脚本不同步，旧包混淆
138 [Normal] 现象：出现 11:55 的 exe 对应 12:41 的场景、12:46 的 demo 对应 13:19 的场景；旧 `freebike2.0` 也在被启动；场景序列化字段会覆盖脚本默认值。
139 [Normal] 根因：改脚本/场景后没有立即重建；多个构建目录并存；Unity 场景字段优先于脚本默认值，改代码不改场景不生效。
140 [Normal] 处理：用文件时间戳对比 exe / Assembly-CSharp.dll / 场景 / 脚本；只勾 panoTest 构建到新目录；改场景 YAML 后再构建；旧包只作备份不启动。
141 [Normal] 验证：多次 MSBuild 0 error；日志中的视频路径与构建时间能对应。
142 [Normal] 状态：已解决，需固化为流程。
143 [Heading 3] D2  视频路径硬编码与旧素材体积
144 [Normal] 现象：视频路径写死 `D:\freebikeapk\...`；StreamingAssets 为空；旧 nighttest/Videos 共约 1.16 GB 会被打进包。
145 [Normal] 根因：PC 演示机可用，但拷贝到其他机器会失效；旧素材无引用却占体积。
146 [Normal] 处理：解析顺序改为 StreamingAssets/pro2 → StreamingAssets 根 → D 盘外部路径；旧视频移到 `_backup_20261027\removed-streaming-assets`；打包后把视频复制到 `_Data\StreamingAssets\pro2\`。
147 [Normal] 验证：日志显示主视频路径正确；备份目录大小约 1.14 GB。
148 [Normal] 状态：已处理；便携交付需按流程复制视频。

152 [Heading 2] 4.1  根因归类
153 [Normal] 15 个问题看似分散，归因后只有五类。把它们分开，才能避免“改错层”：视频卡不是 Unity 逻辑，VR 不进不是场景问题，A1 不通不是 Unity 代码问题。
155 [Heading 2] 4.2  经验清单（可直接复用）
156 [List Bullet] 先查边界再调代码：H.264 先看分辨率是否 >4096、码率是否过高；6K 优先 HEVC。
157 [List Bullet] 先看完整性再查 XR：`icacls` 有 Low 标签、日志有 low integrity，就先换 Medium 目录，不要浪费时间调 OpenXR。
158 [List Bullet] 先 SteamVR 后应用：OpenXR 只初始化一次；用等待 vrserver 的启动脚本。
159 [List Bullet] 只跑一个实例：多实例会抢焦点与 UDP 端口，头显里就是 SteamVR 影院层。
160 [List Bullet] 看日志关键字：`Runtime Name`、`FOCUSED`、`RUNTIME_UNAVAILABLE`、`主视频播不了`、`Failed to create the D3D11 device`。
161 [List Bullet] 改场景再构建：Unity 场景序列化字段优先于脚本默认值；exe/DLL/场景时间戳要对齐。
162 [List Bullet] 视频路径优先 StreamingAssets，外部 D 盘只做开发回退；交付时显式复制视频。
163 [List Bullet] 8K 静态图不是瓶颈；真正的性能大头是每眼渲染分辨率与视频解码。

173 [Heading 2] 5.1  三条结论
174 [List Bullet] 产品层：极简三段式成立，主页/骑行/暂停与 A1 联动逻辑已经落地，这是正确的演示形态。

176 [List Bullet] 交付层：构建目录完整性、SteamVR 启动顺序、单实例、视频路径与素材版本，是比代码更容易翻车的四个交付前置条件。
177 [Heading 2] 5.2  三条建议
178 [List Bullet] 先把 4K 视频换成 baseline/CFR 或 HEVC 4K，闭环“能播”；再谈 6K。
179 [List Bullet] 把“单实例 + 等待 SteamVR + 前台窗口”固化成启动脚本，避免每次手动排障。
180 [List Bullet] 把 OpenXR Profile、D3D11 硬解、6K/4K 参数做成可配置项，形成可复现的演示包。
181 [Normal] 总体判断：项目已经越过“能不能跑”的阶段，进入“能不能稳定演示”的阶段。剩余问题都属于环境/兼容性/流程，不是架构性难题；按 P0→P1 顺序处理即可闭环。
